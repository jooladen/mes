# ⭐ 왜 "모르게" 하나 — 정보 은닉

> 소스를 쪼개다 보면 *"화면은 ~를 모른다"*, *"데이터는 화면을 모른다"* 는 말이 계속 나온다.
> **이게 왜 중요한가. 모르면 어떤 고통을 겪는가. 누가 왜 이 개념을 만들었는가.**
>
> 이 문서는 `23-파일쪼개기-실습-5단계.md` 와 `22-화면에-남는것-나가는것.md` 의 **근거**다.
> 쪼개는 방법이 아니라 **쪼개는 이유**를 다룬다.

---

# ⭐⭐⭐ 한 문장

> # **"안다 = 묶인다"**
>
> A가 B를 **알면** → B가 바뀔 때 **A도 바뀐다.**
> 그러니 **"모른다"는 "안 바뀐다"** 는 뜻이다.

**"모른다"는 게으름이 아니라 보험이다.**

---

# 1. 🟢 생활 예제 두 개

## ① 친구 전화번호

```
내 수첩에 "김철수 010-1234-5678"      ← 내가 번호를 안다
        ↓
김철수가 번호를 바꿨다
        ↓
🚨 내 수첩을 고쳐야 한다
```

**김철수 친구가 100명이면 100명이 다 고쳐야 한다.**
그리고 **1명이 안 고치면 그 사람만 연락이 끊긴다. 본인은 모른다.**

### 반대로 — 카톡 아이디만 안다면

```
김철수가 번호를 바꿨다  →  나는 아무것도 안 한다  →  카톡은 그대로 간다
```

😀 **번호를 "모르니까" 번호가 바뀌어도 상관없다.**

> ⭐ **모르는 것이 곧 안전이다.**

## ② 전등 스위치

**스위치는 전구가 뭔지 모른다.** 백열등인지 LED인지, 몇 와트인지.

```
전구를 LED로 교체  →  스위치는 그대로
```

**만약 스위치가 전구 종류를 알고 있다면?**
→ 전구 바꿀 때마다 **스위치도 뜯어서 교체**해야 한다.

> ⭐ **스위치가 "모르는 것"이 스위치의 기능이다.** 몰라서 안 바뀌는 것이다.

# 2. 📜 누가 왜 만들었나 — 1972년

## 그때 무슨 일이 있었나 — "소프트웨어 위기"

1960~70년대, 프로그램이 커지면서 재앙이 벌어졌다.

| 증상 | |
|---|---|
| **한 줄 고치면 딴 데가 터진다** | 그리고 **어디가 터질지 아무도 모른다** |
| 사람을 더 넣으면 **더 늦어진다** | (브룩스의 법칙) |
| 대형 프로젝트가 **계속 실패** | IBM OS/360 등 |

## 그때의 상식 — "순서대로 쪼갠다"

```
입력 모듈  →  계산 모듈  →  출력 모듈
```

당연해 보인다. **그런데 이게 문제였다.**

> 요구가 하나 바뀌면 → **세 모듈이 동시에 바뀐다.**
> *"금액을 소수점 두 자리로"* → 입력도, 계산도, 출력도 전부 수정.

## ⭐ David Parnas 의 답 (1972)

논문 제목 자체가 질문이다 — **"시스템을 모듈로 분해할 때 무엇을 기준으로 삼을 것인가"**
(*On the Criteria To Be Used in Decomposing Systems into Modules*)

그의 답:

> # ⭐ **"순서로 쪼개지 마라. 바뀔 것을 숨기는 기준으로 쪼개라."**

이것이 **정보 은닉(Information Hiding)** 이다.

| | 쪼개는 기준 | 결과 |
|---|---|---|
| ❌ 그때까지 | **순서** (입력→계산→출력) | 하나 바뀌면 **여럿** 바뀜 |
| ✅ Parnas | ⭐ **바뀌는 이유** | 하나 바뀌면 **하나만** 바뀜 |

## 우리가 오늘 한 것이 정확히 이것이다

```
❌ 순서대로 쪼개기:   조회 → 계산 → 표시

✅ 우리가 한 것:
   orderSeed.js    ← DB가 바뀔 때
   ordersApi.js    ← 계산 규칙이 바뀔 때
   OrderPage.vue   ← 화면 요구가 바뀔 때
```

> 📌 2026-09-06 실습에서 준이 *"데이터부터 빼야겠다"* 고 **감으로** 판단한 것이
> **50년 전 논문의 결론과 같았다.** 감각은 있었고 이름이 없었을 뿐이다.

# 3. 😖 "모르게" 안 하면 겪는 고통 3가지

## ① 연쇄 수정 — 하나 고치면 열 군데

```
서버 주소 변경
      ↓
화면 10곳 수정
      ↓
🚨 1곳 빠뜨림
      ↓
그 화면만 조용히 안 됨 (자주 안 쓰는 화면이라 아무도 모름)
      ↓
한 달 뒤 현업: "이 화면 원래 안 됐어요?"
```

**에러도 안 나고 로그도 안 남는다.** 그냥 안 된다.

## ② ⭐⭐ "이 소스는 건드리지 마세요" ← 가장 무섭다

SI 현장에서 반드시 듣게 되는 말이다.

**왜 이런 말이 생기나?**

> **뭐가 뭘 아는지 아무도 모르기 때문이다.**
> 고치면 어디가 터질지 예측이 안 됨 → 아무도 안 건드림 → 그대로 굳음 → **레거시**

🟢 **집 안 배선이 벽 속에서 뒤엉켜 있는 것.**
스위치 하나 바꾸려는데 **어느 선이 어디로 가는지 몰라서** 아무도 손을 못 댄다.
결국 **그 방은 불이 안 켜지는 채로 산다.**

😀 **"모른다"를 지키면** — 벽마다 배선이 독립이다. 안방 스위치를 바꿔도 거실은 안 건드린다.

> ⭐ **레거시는 코드가 낡아서 생기는 게 아니다. 의존이 뒤엉켜서 생긴다.**

## ③ 테스트 불가

A를 검사하려는데 **A가 B, C, D를 알고 있으면** — B, C, D를 다 띄워야 A를 테스트할 수 있다.

🟢 **국물 간을 보려는데 냄비·가스레인지·주방 전체를 가져와야 하는 것.**

# 4. ⭐ 실무 판단 — 이 질문 하나

> # **"이게 저걸 몰라도 되나?"**
>
> 모르게 할 수 있으면 → **모르게 한다.**
> **아는 만큼 미래에 같이 고쳐야 할 파일이 늘어난다.**

| 알면 | 미래 비용 |
|---|---|
| 화면이 **서버 주소**를 안다 | 주소 바뀌면 **화면 전부** |
| 화면이 **계산식**을 안다 | 규칙 바뀌면 **화면 전부** |
| 화면이 **테이블 구조**를 안다 | 컬럼 바뀌면 **화면 전부** |
| 데이터가 **화면**을 안다 | 🚨 화면 바뀌면 **데이터까지** (최악) |

## 방향은 한쪽뿐

```
화면  →  업무 로직  →  데이터
   ───── 아는 방향 ─────→

데이터가 화면을 아는 것 = 🚨 금지
```

**아래쪽이 위쪽을 알면 안 된다.** 알면 위쪽을 고칠 때마다 아래쪽이 따라 바뀐다.

🟢 **창고는 손님이 누군지 모른다.** 주문서만 본다.
만약 창고 벽에 *"3번 테이블 김씨 → 맵게"* 가 붙어 있다면 — **김씨가 안 오면 창고 벽을 뜯어야 한다.**

---

# 5. 📋 "모르게 하는" 실제 방법

| 방법 | 뜻 | 이 프로젝트의 예 |
|---|---|---|
| **함수로 감싼다** | 안이 어떻게 생겼는지 숨김 | `fetchOrder(no)` — 화면은 SQL도 주소도 모름 |
| **파일을 나눈다** | 열지 않으면 안 보임 | `orderSeed.js` — 화면 파일에 데이터가 없음 |
| **한 곳에만 둔다** | 아는 곳을 하나로 제한 | `http.js` — 서버 주소를 아는 유일한 파일 |
| **이름만 준다** | 값이 아니라 이름으로 부름 | `QUALITY_API.COA_PRINT_DATA` |

> 📌 **네 가지 다 "덜 알게 하는" 방법**이다. 기능을 늘리는 게 아니라 **아는 범위를 줄이는 것**이다.

# 6. ⚠️ 그런데 공짜가 아니다

**모르게 할수록 읽기가 어려워진다.**

| | 다 아는 구조 | 모르게 한 구조 |
|---|---|---|
| 고치기 | 😖 어디가 터질지 모름 | 😀 한 곳만 |
| **읽기** | 😀 한 파일에 다 있음 | 😖 **여러 파일을 따라가야** |
| 역추적 왕복 | 😀 0~1회 | 😖 **4~5회** |

> 📌 2026-09-06 실습 실측: MES(4층, 11파일)는 첫 역추적에 **8왕복**,
> 거래명세서(2층, 3파일)는 **4왕복**이었다. **같은 일인데 2배.**

## ⭐ 그래서 판단 기준

```
지금 안 쪼개서 겪는 고통  <  쪼개서 겪는 고통
        → 쪼개지 마라

지금 안 쪼개서 겪는 고통  >  쪼개서 겪는 고통
        → 쪼개라
```

**크기가 기준이 아니다. 바뀌는 이유가 기준이다.**

| 상황 | 판단 |
|---|---|
| 화면 1~2개, 혼자, 안 바뀔 것 | ❌ **쪼개지 마라** — 한 파일이 이긴다 |
| **바뀌는 이유가 2개 이상 보임** | ⭐ **지금 쪼개라** |
| 여러 화면이 같은 로직을 씀 | ✅ 쪼개라 |
| 나중에 백엔드를 갈아끼울 예정 | ✅ 쪼개라 |

> 😀 **"나중에 쪼개야지"는 괜찮다. "미리 쪼개놓자"가 위험하다.**

```
   ① 전화번호를 알면  → 번호 바뀔 때 내가 고친다
   ② 스위치가 전구를 모르면 → 전구를 바꿔도 스위치는 그대로

   1972 Parnas : "순서로 쪼개지 말고, 바뀔 것을 숨기는 기준으로 쪼개라"

   😖 안 지키면 : 연쇄 수정 / "건드리지 마세요" 코드 / 테스트 불가

   판단 : "이게 저걸 몰라도 되나?"  →  모르게 할 수 있으면 모르게
```
