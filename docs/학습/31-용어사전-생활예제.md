# 1부 — 공장/품질 용어

## Lot (로트)

🟢 **학생 한 명.** 정확히는 **"같은 날 같은 기계로 한 번에 만든 물건 묶음"** 이다.
빵집으로 치면 *"오늘 아침 3시에 한 오븐에 넣고 구운 식빵 50개"* 가 Lot 하나다. 그 50개는 운명을 같이한다 — 오븐 온도가 잘못됐으면 50개가 다 잘못됐다.

🔵 품질 추적의 최소 단위. 불량이 발견되면 **그 Lot 전체를 회수**한다. 그래서 검사도 Lot 단위로 하고 성적서도 Lot 단위로 낸다.
📁 `TRN_LOT` 테이블 / `src/mock/lot.json`

## 검사항목 (Inspection Item)

🟢 **과목.** 인장강도·경도·불순물 = 국어·수학·영어.
🔵 이 물건이 규격에 맞는지 확인하려고 재는 항목. 품목마다 다르다 — 브라켓은 5개, 정밀 샤프트는 30개.
📁 `MST_INSP_SPEC` / F1 화면에서 등록

## 규격 · LSL · USL

🟢 **합격 기준.** "수학 60점 이상"처럼 "인장강도 400~500 MPa".

| 약자 | 뜻 | 🟢 쉽게 |
|---|---|---|
| **LSL** | Lower Spec Limit | **아래쪽 합격선** — 이보다 낮으면 불합격 |
| **USL** | Upper Spec Limit | **위쪽 합격선** — 이보다 높으면 불합격 |

🔵 판정방식이 3가지라 둘 중 하나만 쓰기도 한다:
- `RANGE`(범위형) — 둘 다 씀. `400 ~ 500`
- `MAX`(상한형) — USL만. `≤ 0.5` **(불순물처럼 적을수록 좋은 것)**
- `MIN`(하한형) — LSL만. `≥ 99.5` **(순도처럼 많을수록 좋은 것)**

📁 `src/utils/specFormat.js` 의 `formatSpecRange()`

## 판정 (PASS / FAIL / NONE)

🟢 **과목별 합격 / 불합격 / 아직 안 봄.**

🔵 `NONE` 이 있다는 게 핵심이다. **"안 봤다"와 "봤는데 0점"은 완전히 다르다.**
📁 `src/utils/specJudgeClient.js` 의 `judge()`

## 종합판정 (Total Judge)

🟢 **진급 여부.** 한 과목이라도 떨어지면 진급 불가.
🔵 순서가 중요하다: **하나라도 안 봤으면(`NONE`) → 전체가 `NONE`.** 나머지가 다 100점이어도 진급이 아니다.
📁 같은 파일의 `total()`

## CoA (출하성적서)

🟢 **성적표.** Certificate of Analysis 의 약자.
물건을 대기업에 납품할 때 *"우리 제품 검사했고 다 통과했습니다"* 를 종이로 증명하는 문서.

🔵 **대외 문서**다. 한 번 나가면 고칠 수 없다. 그래서 발행 순간의 값을 **복사해서 저장**한다(스냅샷).
📁 `TRN_COA` / `src/components/CoaSheet.vue`

## 발행 (Issue) · 채번

🟢 **성적표에 번호 붙여서 인쇄하기.** "채번"은 **번호표 뽑기**다 — 은행 가면 뽑는 그 번호표.

🔵 `CoA-20260904-001` 형식. 그날의 마지막 번호 + 1.
**미리보기는 발행이 아니다.** 화면에서 보기만 하고 닫으면 번호가 낭비되고 이력에 유령 행이 남는다. 그래서 [미리보기]와 [발행] 버튼이 따로 있다.
📁 `src/api/http.js` 의 `nextCoaNo()`

# 2부 — 데이터 용어

## `MST_` vs `TRN_` 접두사

🟢 **명부 vs 일기장.**

| 접두사 | 뜻 | 🟢 학교로 | 특징 |
|---|---|---|---|
| **`MST_`** | Master (기준정보) | **학생 명부·과목표** | 자주 안 바뀜. 미리 등록해둠 |
| **`TRN_`** | Transaction (거래/실적) | **출석부·시험 답안지** | 매일 쌓임. 계속 늘어남 |

🔵 이 구분이 왜 중요한가: **지우는 방식이 다르다.** 명부에서 학생을 빼는 건 되지만, 이미 본 시험 답안지를 지우면 안 된다.
📁 `docs/02-design/mes-coa-s1.data-model.md`

## `USE_YN` (사용여부)

🟢 **"이번 학기엔 이 과목 안 함" 표시.** 과목 자체를 없애는 게 아니라 "지금은 안 씀"이라고 붙여두는 것.

🔵 `Y`/`N`. **왜 그냥 지우지 않는가?** 이미 그 과목 시험을 본 학생이 있으면, 과목을 지우는 순간 **그 점수가 미아**가 된다.
📁 F1에서 검사항목을 지우면 → 실적이 있으면 서버가 알아서 `N` 으로 바꾼다 (`http.js` 의 `hasInspResult`)

## Soft Delete (소프트 삭제)

🟢 **지우개로 지우지 않고 "취소선" 긋기.**
공책에서 글자를 지우개로 지우면 뭐가 있었는지 알 수 없다. 취소선을 그으면 *"여기 뭐가 있었는데 지금은 안 쓴다"* 를 알 수 있다.

🔵 `DELETE` 대신 `USE_YN='N'`. 참조하는 데이터가 있으면 실제 삭제는 위험하다.
📁 F1 design §3.1 (D37)

## `LATEST_YN` (최신 여부)

🟢 **재시험 답안지 여러 장 중 "이게 최종" 스티커.**
1차에 380점(불합격), 재시험에 452점(합격)이면 **둘 다 보관**하고 452점에만 스티커를 붙인다.

🔵 검사실적은 덮어쓰지 않고 **행을 계속 쌓는다.** 판정과 성적서는 `LATEST_YN='Y'` 인 행만 본다.
**왜?** *"불합격 났다가 재측정으로 합격됐다"* 는 이력이 품질 추적의 핵심 정보다. 덮어쓰면 사라진다.
📁 `TRN_INSP_RESULT` / F2 design §4

## `sortNo` vs `printSeq` — 헷갈리기 쉬운 한 쌍

🟢 **출석번호 vs 성적표 줄번호.**

- **`sortNo`** = 출석번호. 한 번 정하면 고정. 중간에 전학 가면 **번호가 비어버린다** (1, 2, 5, 9)
- **`printSeq`** = 성적표에 찍히는 줄번호. **항상 1부터 빈틈없이** (1, 2, 3, 4)

🔵 성적표 `No.` 열에 `1, 2, 5, 9` 가 찍히면 *"3번과 4번은 어디 갔냐"* 는 질문을 받는다. 그래서 인쇄 시점에 **1부터 다시 매긴다**(조밀화, dense).
📁 F3 design §3.0 (D3) / `http.js` 의 `buildCoaDetail()`

## 스냅샷 (Snapshot)

🟢 **사진.** 나중에 머리를 잘라도 **사진 속 머리는 그대로**다.

🔵 성적서를 발행하는 순간 규격·측정값·판정을 **복사해서** `TRN_COA_DETAIL` 에 저장한다.
조회할 때 원본 테이블을 조인하지 않는다 — 조인하면 규격이 바뀌었을 때 **이미 나간 문서가 소급 변경**된다.
📁 F3 design §4

## 트랜잭션 (Transaction)

🟢 **계좌이체.** 내 통장에서 돈이 빠졌는데 상대방 통장에 안 들어오면 큰일이다. 그래서 **둘 다 되거나, 둘 다 안 되거나** 둘 중 하나여야 한다.

🔵 검사 저장은 4단계다: ①기존 실적 최신표시 해제 → ②새 실적 삽입 → ③종합판정 계산 → ④Lot 상태 갱신.
③④가 실패하면 ①②도 **되돌린다.** *"실적은 저장됐는데 Lot 상태가 안 바뀐"* 상태가 남으면 F3가 잘못된 Lot을 발행 목록에 올린다.
📁 F2 design §7

## CamelMap

🟢 **통역기.** DB는 `ITEM_CD` 라고 부르고 화면은 `itemCd` 라고 부른다. 같은 걸 다르게 부르니 중간에서 바꿔준다.

🔵 스네이크케이스(`INSP_ITEM_CD`) → 카멜케이스(`inspItemCd`) 자동 변환. **DTO 클래스를 안 만들기 위한 장치**다.
📁 F0 design §3.1

## No-DTO / 응답을 래핑하지 않는다

🟢 **택배 상자 안에 또 상자를 넣지 않는다.** 물건이 바로 나와야 한다.

🔵 서버가 목록을 주면 `[{...}, {...}]` 그대로 준다. `{ success: true, data: [...] }` 로 감싸지 않는다.
감싸면 화면마다 `res.data.data` 를 벗겨야 하고, 성공/실패는 이미 HTTP 상태코드가 말해준다.

> ⚠️ **주의**: "래핑하지 않는다"는 **"DB 행을 그대로 뱉는다"가 아니다.** 계약에 선언된 키만 나가야 한다. 실제로 이 착각 때문에 `custCd` 같은 미노출 컬럼이 새어나간 적이 있다(§3부 참조).

📁 F0 design §4.1

# 3부 — 화면/기술 용어

## Mock (목업)

🟢 **마네킹.** 진짜 사람은 아니지만 옷을 입혀보는 데는 충분하다.

🔵 진짜 서버·DB 없이 **가짜 데이터로 화면을 먼저 만드는 것.**
**왜 먼저?** 식당을 열기 전에 주방 없이 홀부터 꾸며보는 것과 같다. 손님 동선이 되는지 먼저 본다.
📁 `src/api/http.js` (가짜 서버) + `src/mock/*.json` (가짜 데이터)

## Profile (mock / sqlite / oracle)

🟢 **연습용 주방 / 집 주방 / 회사 주방.** 같은 요리를 다른 주방에서 만든다. **레시피(코드)는 안 바뀐다.**

🔵 스위치 하나로 데이터 출처를 바꾸는 장치. 지금은 `mock` 단계이고, 나중에 `sqlite` → `oracle` 로 간다.
이게 가능하려면 **화면이 데이터 출처를 몰라야** 한다. 그래서 화면은 `api/quality.js` 함수만 부르고, 그 안이 뭔지는 모른다.
📁 F0 design §3.3

## 피벗 (Pivot)

🟢 **세로로 늘어선 명단을 가로 표로 눕히기.**

```
[세로 = 서버가 주는 모양]        [가로 = 사람이 보고 싶은 모양]
철수 수학 75                            수학  국어
철수 국어 80          ──▶        철수    75    80
영희 수학 90                     영희    90     -
```

🔵 엑셀 피벗테이블과 같은 개념. **서버는 세로로 주고, 표로 접는 건 화면이 한다.**
**왜 서버가 안 하나?** 서버가 표 모양을 정해버리면 나중에 *"표 말고 그래프로 보여줘"* 할 때 서버를 고쳐야 한다. 재료만 주고 요리는 주방에서.
📁 `src/composables/usePivotGrid.js`

## 동적 컬럼 (Dynamic Column)

🟢 **표의 칸 개수가 조회할 때마다 바뀌는 것.**
학교는 과목이 고정이지만 공장은 품목마다 검사항목 수가 다르다 — 브라켓 5개, 부싱 3개, 샤프트 30개. **미리 표를 만들어둘 수가 없다.**

🔵 조회하고 나서야 *"이번엔 19칸이네"* 하고 컬럼을 만든다. **매번 새로 만든다** — 이전 조회의 컬럼이 남으면 없는 항목 열이 빈 채로 남는다.
📁 `buildDynamicColumns()` / F4 design §4

## RealGrid2

🟢 **비싼 표 만들기 도구.** 무료 표로도 되는 건 무료로 하고, **칸이 매번 바뀌고 수천 줄을 부드럽게 넘겨야 하는 곳**에만 쓴다.

🔵 상용 그리드 라이브러리. 이 프로젝트에서는 **F4에서만** 쓴다. F1 규격 등록 같은 단순 표에는 Quasar `q-table` 로 충분하다.
📁 `src/pages/QualityPivotPage.vue`

## 단위 테스트 (Unit Test)

🟢 **요리 내놓기 전에 소금 맛 보기.**
손님한테 내놓고 *"짜네요"* 소리를 듣는 것과, 내가 먼저 한 숟갈 떠먹어 보는 것의 차이다.

🔵 함수 하나를 떼어내서 *"이 값 넣으면 저 값이 나오나"* 를 자동으로 확인한다.
이 프로젝트에서 **반드시 있어야 하는 건 판정 로직**이다 — `<=` 를 `<` 로 한 글자 잘못 쓰면 **규격에 딱 맞는 제품이 전부 불합격**으로 나간다.
📁 `src/utils/specJudgeClient.test.js` — `pnpm test`

# 4부 — 프로젝트 관리 용어

## 스프린트 (Sprint)

🟢 **한 학기.** "이번 학기엔 여기까지 한다"고 범위를 정해놓고 달리는 기간.
🔵 Sprint-1 = F0~F4 다섯 기능 + 목업까지. 자바 백엔드·로그인은 Sprint-2.

## 품질 게이트 (Quality Gate)

🟢 **진급 시험.** 다음 단계로 넘어가려면 통과해야 하는 관문.

| 게이트 | 재는 것 | 🟢 쉽게 |
|---|---|---|
| **M8** | 설계 완성도 | 계획서를 빠짐없이 썼나 |
| **M4** | 계약 ↔ 구현 일치율 | **설계서에 적은 대로 코드를 짰나** |

🔵 점수가 기준(threshold)을 넘어야 다음 phase 로 간다.

> **이 프로젝트에서 실제로 있었던 일**: M4를 **설계 단계에서** 9번이나 쟀는데 한 번도 통과 못 했다.
> 🟢 **당연했다.** M4는 *"설계서대로 코드를 짰나"* 를 재는 시험인데, **그때는 코드가 한 줄도 없었다.**
> 시험지에 문제가 있는 게 아니라 **답안지를 안 낸 상태에서 채점한 것**이다.
>
> 코드를 다 만들고 다시 재니 M4가 **실제 버그 3개**를 정확히 짚어냈다. 게이트가 제 역할을 한 것이다.
>
> **교훈**: 지표는 **재는 시점**이 맞아야 의미가 있다.

## PDCA

🟢 **계획하고(Plan) → 만들고(Do) → 확인하고(Check) → 고치기(Act).** 방학 계획표 세우고 실천하고 점검하는 것과 같다.
🔵 이 프로젝트의 문서 폴더 이름(`01-plan`, `02-design`, `03-analysis`)이 이 순서를 따른다.

## `D42` 같은 번호는 뭔가

🟢 **결정 번호.** *"왜 이렇게 했지?"* 싶을 때 그 번호로 설계서를 검색하면 **이유가 적혀 있다.**

🔵 설계 중 내린 판단에 붙인 일련번호. 예:
- `D3` — 성적서 줄번호를 1부터 다시 매기는 이유
- `D27` — 비활성 검사항목을 화면에는 보여주되 판정에서는 빼는 이유
- `D37` — 실적이 있는 검사항목은 지우지 않고 비활성화하는 이유

**코드 주석에도 이 번호가 박혀 있다.** 코드에서 `(D37)` 을 보면 설계서에서 `D37` 을 검색하면 된다.

# 5부 — 🕳️ "고장났다고 말 안 해주는 고장" 4종

**이 프로젝트를 만들면서 실제로 겪은 함정들이다.** 넷 다 공통점이 있다:

> **에러 메시지가 안 뜬다. 빌드도 통과한다. 그런데 화면만 틀리다.**

🟢 **자동차로 치면 경고등이 안 들어오는 고장**이다. 시동도 걸리고 소리도 정상인데 브레이크가 안 듣는다.

## ① 없는 서랍에 물건 넣기

🟢 설계도에 *"여기 있는 문에 손잡이를 다세요"* 라고 적혀 있는데, 가보니 **그 자리에 문이 없었다.**

🔵 Quasar `QSelect` 에 `#popup-content` 슬롯을 쓰라고 설계서에 적혀 있었는데, **그런 슬롯은 존재하지 않았다.**
Vue는 없는 슬롯에 넘긴 내용을 **조용히 무시한다.** 에러도 경고도 없이 드롭다운만 안 열렸다.

**어떻게 알았나**: 눌러봤는데 안 열려서. 그리고 **라이브러리 소스에서 슬롯 목록을 직접 확인**했다.
**교훈**: 설계서도 틀릴 수 있다. 라이브러리 API는 **문서 말고 소스에서** 확인한다.

## ② 열쇠 없이 문 열기

🟢 **열쇠가 없으면 문이 안 열리는 게 아니라, 문 자체가 무너진다.**

🔵 RealGrid2는 라이선스 키가 없으면 `LicenseError` 를 **던진다.** 설계서에는 *"평가판으로 동작"* 이라고 적혀 있었지만 사실이 아니었다.
화면 초기화가 통째로 중단되는데, 그 예외를 잡지 않으면 **에러 배너조차 없이 "총 0건"** 만 보인다 → *"데이터가 없나 보다"* 로 읽힌다.

**교훈**: 초기화 코드는 **반드시 try/catch 로 감싸고 실패를 화면에 보여준다.** 조용히 죽으면 원인을 못 찾는다.

## ③ 신고 안 한 짐은 버려진다

🟢 **비행기 수하물에 신고 안 한 물건을 넣으면 말없이 버려진다.** 도착해서 가방을 열어야 없어진 걸 안다.

🔵 RealGrid2는 `setFields()` 로 **선언하지 않은 키를 `setRows()` 때 말없이 버린다.**
판정값을 행 데이터에 담아 보냈는데 선언을 안 해서, 색칠 함수 안에서는 항상 `undefined` 였다 → **이탈 셀이 안 칠해졌다.** 에러도 경고도 없이.

**교훈**: 라이브러리에 데이터를 넘길 때는 **"내가 넣은 게 정말 들어갔나"** 를 한 번 확인한다.

## ④ 서랍째 건네주기

🟢 **친구가 "지우개 좀 빌려줘" 했는데 필통을 통째로 건네준 것.** 안에 뭐가 들었는지 모른 채.

🔵 DB 행을 `{...row}` 로 그대로 응답에 실었더니, **계약에 없는 키가 같이 새어나갔다** — `custCd`(미노출 컬럼), 원소마다 반복된 `coaNo`.

**교훈**: **저장 형태 ≠ 응답 형태.** No-DTO 원칙은 *"래핑하지 않는다"* 이지 *"테이블을 그대로 뱉는다"* 가 아니다. 나갈 키를 **명시적으로 골라서** 만든다.

---

## 그래서 지켜야 할 규칙

```
빌드 통과  ≠  정상 동작
콘솔 깨끗  ≠  정상 동작
테스트 통과 ≠  화면 정상
```

🟢 **만들었으면 반드시 눌러본다.** 네 함정 모두 *"눌러보니 이상하다"* 로만 발견됐다.

🔵 그리고 눌러본 결과를 **문서에 남긴다.** 설계서가 틀렸던 경우가 이 프로젝트에서만 4번 있었다 —
없는 슬롯(§5-①), 라이선스 문구(§5-②), 조회 필터 누락(D39·D41), 상태 필터로 막힌 경로(D41).
**고치고 문서를 안 고치면 다음 사람이 같은 함정에 빠진다.**

# 6부 — 한눈에 보는 약어표

| 약어 | 풀이 | 🟢 한마디 |
|---|---|---|
| **MES** | Manufacturing Execution System | 공장 관리 프로그램 |
